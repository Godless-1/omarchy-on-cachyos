# v1.4.4 - Duplicate Ditto

> ## ⚠️ DO NOT INSTALL - superseded, two known bugs
> Use the [latest release](https://github.com/Godless-1/omarchy-on-cachyos/releases/latest) instead.

**Duplicate Ditto.** A boot menu entry with the right name that would not boot, and one with the wrong name that did.

A machine came back from a routine 52-package upgrade with two entries in the limine menu for one installation: `CachyOS` and `Arch Linux`. Selecting `CachyOS` showed an error. Selecting `Arch Linux` booted normally. Nothing was corrupt, and the initramfs was never stale — the upgrade contained no kernel, no `systemd`, no `cryptsetup`, no firmware, and the rebuild hook was right not to fire.

`limine-entry-tool` titles its top-level OS entry from `NAME`/`PRETTY_NAME` in `/etc/os-release`, and keys on that title. Change the distribution name — which is exactly what Omarchy does, and what `preserve-cachyos-identity.sh` undoes — and the next kernel event does not rename the existing entry. It writes a new one under the new name and abandons the old. The abandoned block keeps the kernel and initramfs hashes it had on the day it was orphaned, and CachyOS ships `ENABLE_VERIFICATION=yes`, so limine checks those hashes, finds they no longer match the files on disk, and refuses to load. The entry that still carried the distribution's own name was the dead one.

This is this project's own doing. Restoring the identity was the right thing; leaving the bootloader to notice on its own was not.

Three changes, in the order they would have caught it:

- **`preserve-cachyos-identity.sh` now says to run `limine-update`** after changing the identity, because that renames the entry in one step instead of leaving a duplicate for the next kernel update to create.
- **`verify-reboot-safety.sh` fails when more than one top-level entry claims your machine-id**, names the recovery commands, and says plainly that booting is not at risk meanwhile — the live entry still works. Top-level entries write that comment unindented and snapshot sub-entries indent theirs, which is the whole reason the check can tell fifty snapshots from two operating systems.
- **`--rebuild` stops choosing its tool by the wrong question.** It used to run `limine-mkinitcpio` only when `/etc/mkinitcpio.d` was empty, and otherwise fall through to `mkinitcpio -P`, which rebuilds the image without touching the entries or their hashes — the same drift, arrived at deliberately. limine ships `/usr/local/bin/mkinitcpio` purely to warn about that, and then stops to ask a question an unattended run would hang on. The bootloader decides now, not the presets.

The installer also copies `/boot/limine.conf` into its backup directory. It was already saving `pacman.conf` and `mkinitcpio.conf` and not the one file this failure actually damaged, which meant there was no before-and-after to compare when it happened.

`docs/troubleshooting.md` gains the symptom, the cause and the by-hand recovery. `PROVENANCE.md` records the defect and that it traces back to earlier advice in this project to symlink `/etc/os-release`, which is what put `Arch Linux` in the menu in the first place.

Nine suites, 162 assertions. Code AGPL-3.0-or-later, docs CC-BY-SA-4.0.

## Known bugs shipped in this version

**The new duplicate-entry check reported a non-blocking fault as a failure.** A failure makes the verdict print `DO NOT REBOOT` in red - directly above the finding's own sentence saying booting was not at risk. The live entry boots; that is how the machine reporting the fault was running while it read the warning. Fixed in 1.4.5.

**That check counted comments, not entries.** The rule matched unindented `comment: machine-id=` lines as a stand-in for boot entries. Removing an OS entry leaves the comment that preceded it behind, so the first run after a successful repair still reported a duplicate that was already gone. Fixed in 1.4.5.
